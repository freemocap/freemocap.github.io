# Engineer callouts

Things found while updating the docs-v2 content against the app that the docs can't fix on
their own. Each one needs an engineer to fix something in the app, its repo, or the website, or to
answer a question. Checked against freemocap `main` at v2.0.0-alpha.25 (75c8acc2) unless noted.

Not published: this file sits outside the folders the docs site builds from.

|---|---|---|---|

| 8 | App: calibration "Download ChArUco Board" button | The button in the calibration help tooltip opens `docs.freemocap.org/documentation/multi-camera-calibration.html`, a v1 docs URL. | 9 | App repo: ChArUco board files | The app's default board is 5x3 with 54 mm squares, but the only board image in the repo (`shared/charuco/charuco_board_image.*`) is a 7x5 board. | 10 | App source: recording folder layout | `freemocap/system/recording_structure/recording_structure.py` calls itself "the authoritative source of truth" for the recording folder layout and describes `videos/synchronized/`, `videos/annotated/`, `output/` and `{name}_data.parquet`. But the app actually writes `synchronized_videos/`, `annotated_videos/` and `output_data/`. The docs follow what's written to disk. Worth a note in that file, or finishing the migration. | 2026-10-14 |
| 11 | App: camera exposure on Mac | skellycam's `opencv_extract_config.py` notes "macOS always returns 0 for exposure". Does the manual exposure setting actually take effect on Macs? The docs currently say exposure is set per camera with no platform caveat except Linux. | 2026-10-14 |
| 12 | App: calibration quality | The app never shows the calibration's reprojection error. It's only in the calibration TOML (`[metadata] reprojection_error_px`) and the logs. The docs tell people to look in the TOML. Showing it in the Calibration panel after "Calibrated", with a rough good/bad guide, would help a lot. Engineers: is there a threshold we can publish as "good"? | 2026-10-14 |
| 13 | App: Import Videos synchronization | Synchronizing imported videos needs `ffmpeg`, which the installers don't include (`check_ffmpeg.py` looks for it on PATH). Installer users have to install ffmpeg themselves and restart. Can the installers bundle it? The docs currently tell people to install it. | 2026-10-14 |
| 14 | Docs repo: earlier style pass | A previous automated Vale fix replaced a word (probably "disabled") with the garbled text "turn off' or 'off" in `guides/posthoc-mocap.md` and `guides/camera-setup.md`, and lowercased UI labels ("Continue to mocap Setup", "Process mocap"). Both pages are now rewritten. No other pages had it. FYI for whoever runs bulk Vale fixes. | 2026-10-14 |
| 15 | Zenodo / CITATION.cff | Zenodo's latest archived version is v2.0.0-alpha.22 (2026-08-27); alpha.23 to alpha.25 aren't archived. `CITATION.cff` still says `version: 2.0.0-alpha.21` and `date-released: 2026-08-11`. Is `publish-zenodo.yml` meant to run on every release, and should bumpver update `CITATION.cff`? | 2026-10-14 |
| 16 | SkellyLogs version pinned in FreeMoCap | Resolved on the docs side: `SKELLYLOGS_LOG_DIR` exists on SkellyLogs `main`, but FreeMoCap alpha.25's `uv.lock` pins a commit 11 commits behind, which doesn't have it. The stub pages now say so. Worth bumping the pin at some point. | 2026-10-14 |
| 17 | App output: `reprojection_error` column | The parquet's `reprojection_error` column is always `NaN`. `skeleton_from_mediapipe_observations.py` computes reprojection error during triangulation but builds the `Human` without attaching it, so skellymodels writes NaN. The docs now say the column is empty. Wiring it through would give users a per-point quality score. | 2026-10-14 |
| 18 | App: RTMPose recordings without a ground plane | When a multi-camera recording has no ground-plane calibration, the app tries to stand the skeleton upright (`Human.put_skeleton_on_ground`), but that needs MediaPipe foot names (`left_foot_index`, `right_foot_index`). RTMPose has `left_big_toe` instead, so it's skipped. With default settings (RTMPose, ground plane off) the skeleton comes out lying on its side. Either map the RTMPose toe names, or turn ground-plane alignment on by default. | 2026-10-14 |
| 19 | App output: `tracker_schema.json` | `posthoc_mocap_task.py` always saves the RTMPose wholebody definition to `tracker_schema.json` (`definition = RTMPOSE_WHOLEBODY_DEFINITION`), even for MediaPipe recordings. Anyone reading that file for a MediaPipe recording gets the wrong point names. The skeleton models reference page already warns about this. | 2026-10-14 |
| 20 | SkellySync branch | FreeMoCap's `pyproject.toml` installs SkellySync from the `philip/rewrite` branch, not `main`. `main` (and the PyPI package) is the old PySide6 version. Once the rewrite is stable, merging it to `main` (and releasing it) would let the docs and installs point at one version. | 2026-10-14 |
| 21 | Sub-repo READMEs and PyPI packages | SkellyForge's GitHub README still describes a FreeMoCap 1.x post-processing GUI (conda, Python 3.9/3.10), and the repo has no description. The Blender add-on README points at v1 paths (`freemocap_data/recording_sessions`) and v1 test data. The PyPI releases of skellytracker, skellyforge and skelly-synchronize are older than what FreeMoCap uses, and their GitHub "Releases" stop in 2023. | 2026-10-14 |
| 22 | App: Import Videos on macOS | With Homebrew's ffmpeg installed, the Import Videos dialog still says "Could not find ffmpeg and ffprobe on your system PATH" when the app is opened from the Dock or Finder, because GUI apps don't have `/opt/homebrew/bin` on their PATH. It finds ffmpeg only when launched from a shell with that PATH. Could the app also look in the usual Homebrew locations, or let users set the ffmpeg path? Seen in the installed alpha.25 app on macOS. | 2026-10-20 |
| 23 | Playback: sample data videos | The official `skellysamples` videos (`freemocap_sample_data.zip`, `freemocap_test_data.zip`) are encoded as MPEG-4 Part 2 (`mpeg4`), so Playback shows "Video format not supported by this player" for every camera. Re-encoding to H.264 fixes it. Either the player needs a fallback or the sample data should be re-encoded. The `skellysamples` README is also empty. | 2026-10-20 |
| 24 | Process Mocap: calibration file | After **Calibrate > Import .toml file** the panel shows **Calibrated**, but **Process Mocap** stays disabled ("No calibration file found") until a `{name}_camera_calibration.toml` exists inside the recording folder. The import doesn't copy it there. Changing the processing folder also resets the calibration. The docs say importing a `.toml` is enough. | 2026-10-20 |

Renaming them in the `.toml` fixes it. Worth matching by suffix, or updating the sample calibration. | 2026-10-20 |
